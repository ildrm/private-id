# PrivateID project review and improvement plan

> Historical baseline review. Findings, probes, and source-line references below describe commit `128c25c`. See the [implementation status](IMPLEMENTATION_STATUS.md) and [validation record](IMPLEMENTATION_VALIDATION.json) for the corrected v0.2 implementation.

Review date: 7 September 2026. Baseline: commit `128c25c` in `iranbroker-next`. The application in this repository is **PrivateID**, a Fastify/TypeScript identity service with a React/Vite frontend and Stripe billing; it is not a Next.js brokerage application.

**Recommendation: treat the current implementation as a development prototype. Do not approve production identity decisions or paid-service launch until the release gates below pass.** The project has useful foundations, but its most consequential advertised guarantees are incomplete. Passing the existing test suite does not establish safe administrator enrollment, revocation, transaction durability, correct billing, or complete customer workflows.

This is a repository review, not a certification or a claim that every possible defect has been discovered. Findings distinguish reproduced behavior, direct source evidence, and product decisions that need an explicit specification. Application source was not changed. This review directory contains the report and supporting evidence.

## 3. Findings and required changes

### Identity, authentication, authorization, and privacy

**F01 — P0 — Public signup can claim bootstrap administrator privileges.** Owners: R5, R6. Reproduced by S01. `applyBootstrap` matches a supplied email address against `PRIVATEID_BOOTSTRAP_ADMIN_EMAILS` and assigns all five roles. Registration performs no mailbox challenge and sets `emailVerified: true`. An attacker who registers an allowlisted address before its owner can become a security administrator. The deployment must have the allowlist configured for this path to apply. Reapplying the grant on every login also reverses a later demotion while the allowlist remains configured, and the grant itself has no dedicated audit event. Evidence: [src/app.ts:5](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:5), [src/app.ts:12](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:12), [src/app.ts:13](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:13), [src/domain.ts:60](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:60).

Replace email-triggered bootstrap with a one-time operational enrollment tied to a known account ID, verified ownership, and mandatory staff MFA. Persist and audit the enrollment transaction; consume its bootstrap authority permanently. Acceptance: public signup with an allowlisted address never grants privilege; demoted accounts stay demoted; repeated/concurrent enrollment cannot create extra administrators.

**F02 — P0 — Administrative suspension does not revoke existing authorization.** Owners: R5, R6. Reproduced by S02. `PUT /admin/customers/:id/assurance` can set `accountValid: false`, but `authenticate()` only checks session expiry and user existence. Previously issued sessions still access customer endpoints and can reach proof and billing actions. Evidence: [src/domain.ts:63](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:63), [src/app.ts:38](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:38).

Introduce an explicit account status, check it on every authenticated operation, and atomically revoke sessions/refresh grants when status changes to suspended or deleted. Acceptance: all existing sessions immediately fail after suspension, including sessions belonging to privileged accounts; new login also fails; authorization caches cannot extend access.

**F03 — P0 — Approved proofs remain usable after connected-access revocation, account deletion, or credential revocation.** Owners: R3, R4, R6, R7. Three S03 probes reproduced this. Verification checks the request's approved status and token equality, but not account status, access revocation, source credential state, or verifier state. Deletion and connected-app revocation mainly deny pending requests. Evidence: [src/domain.ts:65](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:65), [src/domain.ts:75](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:75), [src/domain.ts:79](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:79).

Specify whether revocation is immediate or permits a documented residual lifetime. Given current product promises, use immediate server-side invalidation: link proofs to their sources and authorization versions; recheck these conditions and consume the proof within one transaction. Acceptance: proofs issued before each revocation fail afterward, including concurrent verification/revocation cases. Revocation cannot erase claims already disclosed to a relying party; communicate that boundary explicitly.

**F04 — P1 — Session-management identifiers are the bearer credentials themselves.** Owners: R5, R6, R9. Reproduced by S04. `/sessions` and the privacy dashboard return every session map key, and those keys are accepted by `authenticate()`. A compromised session can harvest all of the user's other still-valid tokens, making targeted session revocation less effective. The frontend prints these identifiers and stores its bearer in localStorage. Evidence: [src/app.ts:17](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:17), [src/domain.ts:50](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:50), [src/domain.ts:78](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:78), [web/src/main.tsx:7](/Users/shahinilderemi/Documents/tmp/iranbroker-next/web/src/main.tsx:7), [web/src/main.tsx:21](/Users/shahinilderemi/Documents/tmp/iranbroker-next/web/src/main.tsx:21).

Separate public session IDs from random secrets; store only token hashes; return safe device/creation/last-use metadata. For the same-origin web app, choose a server-managed HttpOnly/Secure/SameSite session design with appropriate CSRF protection, or document and mitigate the explicit bearer design. Acceptance: listed IDs cannot authenticate; revoked tokens fail; authenticated data responses use a deliberate no-store policy.

**F05 — P1 — Account recovery and stronger staff authentication are absent.** Owners: R5, R2, R6. No mailbox verification challenge, password change/reset, recovery-code workflow, or MFA/passkey flow exists. The SQL `mfa_enabled` field is unused. Authentication also has no account-scoped throttling or breached-password policy; nonexistent email login avoids scrypt, unlike existing-account login. Evidence: [src/domain.ts:58](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:58), [src/domain.ts:62](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:62), [migrations/001_initial.sql:2](/Users/shahinilderemi/Documents/tmp/iranbroker-next/migrations/001_initial.sql:2), [web/src/main.tsx:19](/Users/shahinilderemi/Documents/tmp/iranbroker-next/web/src/main.tsx:19), `SECURITY.md`.

Implement verified account entry and recovery with short-lived, hashed, single-use challenges; invalidate sessions after sensitive recovery events; require step-up/MFA for staff actions. Add per-account and per-source abuse controls with bounded work. Acceptance: challenge replay, account enumeration behavior, brute force, recovery takeover, and staff step-up have negative-path tests. Avoid lockout policies that let attackers permanently disable an account.

**F06 — P1 — Global staff roles are mixed with the commercial promise of team workspaces.** Owners: R1, R5, R7. Credential issuers can issue/revoke for any account; roles and capabilities have no organization boundary. Business advertises team roles and issuer/verifier features, but purchasing a subscription changes neither roles nor scope. Evidence: [src/domain.ts:66](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:66), [src/domain.ts:67](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:67), [src/app.ts:4](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:4), [src/app.ts:37](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:37), `docs/BILLING_AND_PLANS.md`.

Decide whether issuer/verifier customers are organizations or vetted platform staff. For organizations, add memberships and scoped permissions; keep platform identity/security administration separate. Never solve the paid-feature gap by automatically granting global `IDENTITY_ADMIN` or `SECURITY_ADMIN`. Acceptance: organization A cannot read or mutate organization B's resources; upgrading cannot grant staff authority; role documentation matches the tested permission matrix.

**F07 — P1 — “Deletion” is indefinite deactivation without an implemented retention lifecycle.** Owners: R11, R1, R6, R8. Deletion retains email, password hash, profile attributes, credentials, proof tokens, and audit/consent histories in the snapshot. There is no purge/anonymization scheduler, restoration-from-backup policy, or billing cancellation integration; deleting a paid account can leave a subscription active while preventing portal login. Evidence: [src/domain.ts:65](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:65), [src/domain.ts:54](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:54), `DATA_MODEL.md`, `docs/PRODUCT.md`.

Define deactivation, deletion request, retained records, and completed erasure as distinct states. Inventory each field and purpose, decide cancellation semantics, and implement deletion jobs with retry and completion evidence. Obtain jurisdiction-specific review of the chosen retention rules; this review does not determine legal retention periods. Acceptance: only the documented retained fields remain after deadlines; deletion retries are safe; backups and reimports cannot silently resurrect active accounts or charges.

**F08 — P1 — The audit trail is neither immutable nor complete.** Owners: R5, R7, R11, R13. Audit events are a mutable array inside a repeatedly overwritten JSON row; the separate `audit_log` table is unused. Deleting a session through `/sessions/:id` emits no audit event; bootstrap grants are unaudited. Failed logins contain little investigatory context, and many authorization/verification failures produce no domain audit record. Evidence: [src/domain.ts:54](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:54), [src/domain.ts:57](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:57), [src/app.ts:18](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:18), [src/app.ts:5](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:5), [migrations/001_initial.sql:8](/Users/shahinilderemi/Documents/tmp/iranbroker-next/migrations/001_initial.sql:8).

Write append-only events in the same transaction as sensitive mutations using restricted database permissions. Define required actor, target, outcome, reason, policy version, and correlation fields; redact secrets. Use an external immutable archive if the threat model requires protection against database operators. Acceptance: privileged changes always have a corresponding event, ordinary app credentials cannot rewrite history, and audit retention is enforced without retaining unnecessary identity data.

### Persistence, concurrency, and algorithms

**F09 — P0 — One persistence error permanently disables subsequent saves.** Owners: R7, R6, R13. D02 reproduced a first save failure followed by zero further save attempts. `pending = pending.then(save)` retains a rejected promise forever. Domain objects were already mutated, so memory can diverge from durable storage. The global `onSend` hook then waits on that rejection for unrelated requests. Evidence: [src/domain.ts:56](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:56), [src/app.ts:9](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:9).

Move state changes into explicit repository transactions; publish successful results only after commit. As containment, make persistence failure move the instance out of readiness and stop accepting mutations, with a recoverable state-reload strategy. Simply adding `.catch()` and continuing is insufficient because partially applied in-memory mutations remain. Acceptance: injected save failures do not report success, do not silently affect later requests, and recovery restores a consistent committed state.

**F10 — P1 — Snapshot persistence shares mutable references.** Owners: R7, R6. D03 reproduced a role mutation made after snapshot creation appearing in that earlier snapshot. Arrays such as audits and the objects stored in maps are not cloned. Bootstrap mutations also occur after the domain schedules persistence and do not independently call `changed()`, making persistence timing significant. Evidence: [src/domain.ts:54](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:54), [src/domain.ts:56](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:56), [src/app.ts:12](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:12).

Use transaction inputs and immutable values; avoid live object references crossing commit boundaries. Deep-copying and versioning snapshots is a temporary mitigation, not the final database model. Acceptance: a queued commit contains only its intended changes; unauthorized/direct object edits cannot be persisted accidentally; bootstrap and role mutations commit with their audit events.

**F11 — P1 — Concurrent registration bypasses uniqueness checks.** Owners: R7, R6. D01 created two accounts with the same email. The uniqueness lookup happens before asynchronous scrypt, so two calls can both pass. Verifier registration uses the same check-before-await pattern and can overwrite a client ID. Declared SQL unique constraints do not protect these records because the application stores them in JSON. Evidence: [src/domain.ts:59](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:59), [src/domain.ts:60](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:60), [src/domain.ts:76](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:76).

Enforce canonical email and client-ID uniqueness in the actual authoritative store, inside the transaction that creates the record. Map constraint violations to stable conflict errors. Acceptance: simultaneous attempts produce one account/application and deterministic conflicts; no returned client secret belongs to an overwritten application.

**F12 — P1 — Two competing data models exist, and nearly all identity indexes are unused.** Owners: R7, R6, R15. PostgreSQL probes found one runtime user and zero rows in `users`. The normalized users, credentials, proof requests, consent, session, verifier, trust, and audit tables are not used by the runtime. Billing uses separate relational tables without account foreign keys. `DATA_MODEL.md` does not explain this operational reality. Evidence: [src/state-store.ts:1](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/state-store.ts:1), `migrations/001_initial.sql`, `migrations/003_platform.sql`, `migrations/004_billing.sql`.

Choose relational repositories as the authority; map every snapshot field, including fields missing from current normalized tables. Backfill with canonicalization/conflict reports, foreign keys, validated claim schemas, and reconciliation counts. Acceptance: all business writes reach the documented tables, normalized and legacy read models agree during cutover, and no migration silently drops roles, evidence, token invalidation, or billing associations.

**F13 — P1 for deployment fencing; P2 for scaling — Multiple instances overwrite committed data and accept the same proof twice.** Owners: R7, R13, R4. Both behaviors reproduced with real PostgreSQL. `runtime_state.version` increments but is never compared; hydrated instances carry independent replay sets. `DEPLOYMENT.md` correctly prohibits multiple replicas, so this is a known architecture limit, not a newly discovered supported-mode promise. Overlapping rollouts or a second operator-started process can still violate it. Evidence: [src/state-store.ts:1](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/state-store.ts:1), [src/domain.ts:75](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:75), `DEPLOYMENT.md`.

Enforce a singleton lease/fencing mechanism immediately. Replace replay state with an atomic conditional database consume/unique insert and replace global snapshot overwrites with row transactions before enabling overlap or replicas. Acceptance: exactly one consume succeeds under concurrency; a stale process cannot commit; a deployment cannot start two active writers accidentally.

**F14 — P1 — Data growth creates increasing latency and an unbounded persistence backlog.** Owners: R14, R7, R13. Every mutation rebuilds global collections and serializes the full snapshot; every response waits on the global save queue. Sessions, used JTIs, requests, audit events, and revocations have no expiry cleanup. `resolveClaim` scans all credentials for every claim; admin customer listing issues one subscription query per user. Evidence: [src/domain.ts:50](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:50), [src/domain.ts:54](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:54), [src/domain.ts:69](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:69), [src/domain.ts:78](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:78), [src/app.ts:36](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:36).

Use indexed account-scoped reads, bounded pagination, transactional row writes, expiry jobs, backpressure, and aggregate/batch subscription queries. Current costs include O(total state) serialization per mutation, O(requested claims × global credentials) claim resolution, and O(users) billing queries per admin page; privacy history adds repeated per-client scans. Acceptance: fixed page sizes bound memory/query counts, expiry jobs cap temporary records, and agreed load tests meet budgets without a continuously growing queue. No production latency number is asserted from static complexity alone.

**F15 — P2 — Migrations and snapshot hydration lack evolution safeguards.** Owners: R7, R13. Migration existence is checked outside the transaction with no migration lock/checksum; simultaneous migrators can race. Snapshot hydration accepts `any`, silently defaults missing collections, and has no schema-version validation. Evidence: [src/database.ts:9](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/database.ts:9), [src/domain.ts:55](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:55).

Run controlled migration jobs with an advisory lock, checksums, explicit database roles, and bounded timeouts. Version persisted payloads while they remain, and reject incompatible/corrupt data with an actionable startup error. Acceptance: concurrent migration runners converge, tampered historical migrations are detected, and old/corrupt snapshots are transformed or rejected predictably. Existing migrations did apply and rerun successfully in the isolated database.

### Credentials, proofs, and relying parties

**F16 — P0 — Identity claims have no enforceable trust/evidence model.** Owners: R3, R4, R1. All credentials carry the same hardcoded `mock-trusted-identity-provider` issuer. The trust registry is never consulted by issuance or claim resolution. Staff can set identity, uniqueness, KYC, and investor booleans without evidence references, method, reviewer rationale, validity period, or jurisdiction-specific policy. Evidence: [src/domain.ts:66](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:66), [src/domain.ts:69](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:69), [src/app.ts:38](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:38).

Define a typed claim catalog and evidence model before enabling real decisions. Bind each credential to an authenticated issuer identity, issuer authority for the claim type, assurance level, evidence reference, review policy, and validity interval. Acceptance: untrusted/suspended issuers cannot contribute accepted claims; an audit can explain why a claim was true at issuance; missing evidence never becomes verified by default. Keep synthetic issuance explicitly isolated until then.

**F17 — P1 — Claim resolution uses insertion order and inconsistent fallbacks.** Owners: R3, R14, R6. I02 showed an older low-assurance true credential overriding a newer high-assurance false credential. I03 showed revoked KYC evidence falling back to a permanent true account boolean. Unknown claims become false, conflating “unsupported/unverified” with a verified negative. Country is merely a two-character string; age derives from JavaScript dates with unspecified timezone/leap-day policy. Evidence: [src/domain.ts:70](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:70), [src/domain.ts:71](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:71), [src/domain.ts:72](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:72), [src/app.ts:38](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:38).

Use deterministic resolution by issuer authority, policy, assurance, freshness, and conflict rules. Represent unavailable, expired, conflicting, and verified-negative results separately. Define age using a validated calendar date and explicit evaluation date; inject the clock for boundary tests. Acceptance: ordering credentials cannot change the result; conflicts fail safely or follow a documented rule; revocation never silently restores a superseded claim; leap-day, birthday, invalid-date, and jurisdiction tests pass.

**F18 — P0 — Disclosure claims can overwrite proof security fields.** Owners: R4, R6. I01 registered `exp` as a requested claim, issued a credential with an expiration value in 2100, and verified the resulting proof. `...claims` is spread after `iss`, `aud`, `sub`, `iat`, `exp`, `jti`, and `proof_request_id`. This requires privileged issuer/verifier configuration; it is not an ordinary user self-assertion exploit. Evidence: [src/domain.ts:74](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/domain.ts:74), [src/app.ts:20](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:20), [src/app.ts:29](/Users/shahinilderemi/Documents/tmp/iranbroker-next/src/app.ts:29).

Place disclosures under a separate typed `claims` property and reserve the full security namespace. Enforce a schema/registry at issuance, request creation, and verification. Acceptance: reserved fields can never be supplied as user/domain claims; maximum lifetime and pairwise subject are invariant regardless of credential content.

## 4. What should be preserved

Keep the single deployable monolith unless measured requirements justify a distributed deployment. The current stack is adequate for a coherent service after transaction boundaries and domain rules are repaired. Preserve the strict public-registration schema that rejects role/assurance fields, scrypt with random salts and constant-time hash comparison, server-side role checks, audience/signature/replay checks as useful foundations, parameterized runtime SQL, actual raw-body Stripe signature verification, dedicated billing ownership, non-root runtime container user, and separation from sibling-product databases. These are useful controls; none substitutes for the missing end-to-end guarantees.

Do not begin with a framework rewrite, microservices, an unrelated new database, or visual polish. The evidence points first to authorization, trustworthy claims, durable state transitions, payment processing, and complete user journeys.

## 5. Target implementation and invariants

Keep a Fastify modular monolith with explicit account/session, organization/authorization, credential/issuer, consent/proof, verifier/federation, billing/entitlement, audit/privacy, and operations modules. Route handlers should validate/authorize, invoke one application use case, and serialize a typed result. They should not mutate service maps or coordinate persistence through `onSend`.

| Domain | Required durable records / boundary | Core invariant |
| --- | --- | --- |
| Accounts | Account status, canonical email, verification and recovery challenges | Unverified public identity cannot acquire staff authority; inactive accounts cannot authorize |
| Authorization | Staff grants separately from organization membership and permission scope | A paid plan never implies platform-wide privilege |
| Sessions | Public ID, secret hash, issued/expiry/revoked timestamps, safe metadata | A listed management ID cannot authenticate; suspension revokes all usable authorization |
| Credentials | Issuer ID, schema/type, claims, assurance, evidence references, validity, revocation/version | Every accepted claim has an authorized source and deterministic policy explanation |
| Verifiers | Client identity, owned redirects, hashed credentials, environment and reviewed lifecycle | Suspended or unreviewed clients cannot obtain production proof redemption |
| Consent/proofs | Request expiry/context, approved claim schema, evidence/version references, issued/consumed timestamps | Decision, issuance, revocation checks, and one-time consumption have transactional semantics |
| Billing | Provider mapping, event inbox, subscriptions/items, invoices/payments, reconciliation operations | Durable event receipt is distinct from successful application; retries converge |
| Entitlements | Catalog version, effective plan, usage ledger/period, organization scope | Quotas and access are enforced atomically using the defined subscription-state policy |
| Audit/privacy | Append-only events, retention classification, deletion requests/jobs | Sensitive transitions and erasure outcomes have minimal, durable evidence |

The normalized migrations already present are a starting point, not a ready replacement: they lack several runtime fields, the intended organization model, proof-consumption data, and stronger lifecycle constraints.

For proof resolution, index credentials by subject and claim/type, evaluate one captured clock value, exclude invalid/untrusted evidence, resolve conflicts with an explicit policy, and produce a typed result plus provenance. For proof verification, validate the cryptographic envelope first, then atomically check current authorization/source versions and consume the proof. For billing, durably receive a signed event, apply or retry its projection, and reconcile independently of event arrival order.

## 7. Database migration and rollback plan

1. **Inventory and reconcile:** count every snapshot collection, inspect canonical-email/client-ID duplicates, validate roles and statuses, identify orphan billing mappings, and classify data/secret retention. Export an encrypted backup and prove it can restore before migration.
2. **Expand the schema:** introduce missing runtime fields, organizations if selected, real session secret hashes, evidence/issuer relationships, proof lifecycle/consumption, event inbox, and append-only audit. Add necessary uniqueness/foreign-key/check constraints after resolving existing conflicts.
3. **Backfill deterministically:** transform a versioned snapshot with a repeatable migration. Produce record counts and hashes/manifests for reconciliation. Do not print secrets or identity claims in migration logs. Preserve pairwise identity continuity and explicitly invalidate legacy proofs if their security semantics cannot be maintained.
4. **Verify before cutover:** compare account access, credentials, proof history, entitlements, and billing totals against the old view using synthetic and sanitized checks. Do not deploy naive dual writes that can diverge; use a bounded maintenance window or an explicitly transactional bridge.
5. **Cut over one writer:** checkpoint/fence the old writer, switch the application to repositories, reconcile again, then run restart/revocation/webhook smoke checks. Monitor errors, orphan records, and lag before widening traffic.
6. **Rollback deliberately:** retain the original snapshot and a schema-compatible image, but never restore old replay or billing projections in a way that re-enables consumed proofs or resurrects canceled access. Record post-cutover writes; prefer a forward repair once writes have moved to the new authority.
7. **Retire legacy state:** only after the agreed observation/recovery period, remove unused schema or runtime snapshot paths and update operations documentation. Multi-instance deployment remains fenced until separately qualified.

## 10. Decisions needed before expanding implementation

The report can be acted on immediately for reproduced bugs; the following product decisions govern the larger design:

- Is the next milestone a synthetic demo, a closed pilot with vetted issuers, or general production identity verification?
- Are issuer/verifier users platform staff or paying organizations, and what data can each organization control?
- Which evidence sources and review policies establish adult status, unique person, KYC, investor eligibility, and signatory authority?
- Is the integration an online centralized proof redemption service, an interoperable identity provider, or a credential-wallet protocol? Which responsibilities belong to each relying party?
- What does revocation promise for unused proofs and already disclosed data, and what is the permitted residual lifetime?
- What constitutes proof usage, which subscription statuses retain access, and what happens to paid billing on account deletion?
- What scale, availability, recovery, and retention requirements define the release gate?

My recommended default is a **closed pilot with one explicit assurance policy, vetted issuers/verifiers, a transactional PostgreSQL authority, a safe federation exchange, complete customer revocation controls, and paid plans deferred until billing/entitlements pass their gates**. Keep broader Business/team and proof-provider expansion behind the scope decision. This preserves the useful implementation while making the next milestone concrete and verifiable.
